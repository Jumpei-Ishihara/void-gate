## 2. 各フェーズの進め方（共通手順）

1. **RED**: `tests/phaseFn.js` を詳細設計の §4 に沿って作成し、実行して**失敗することを確認**
2. **既存テストの改訂**: 詳細設計の §5 にある意図的な仕様変更だけを反映（改訂理由をテストのコメントに残す）
3. **GREEN**: 実装 → phaseFn 全合格
4. **回帰**: `run-all.js` にスイートを追加し全実行 → 全スイート合格
5. **目視**: プレビューで PC / SP（横画面）のスクリーンショットを確認
6. **commit → push → Pages 反映確認**（本番 URL で起動・コンソールエラーなし）
7. 仕様書の状態を `Verified (日付・件数)` に更新

## 3. フェーズ別の要点

### F1 当たり判定
- 最初にテストで「旧判定の誤り」（翼の貫通 / クレーター側の誤被弾）を再現してから置換する（F1-T04/T05 は RED で確実に失敗する）
- 寛容係数 `HIT_LENIENCY = .9` は定数1つ。実プレイ後の調整はこの値のみ

### F2 照明・ACES（本計画で最も慎重に進めるフェーズ）
- **実装の前に基準値を取る**: 輝度プローブ（`lookProbe`）だけを先に実装し、現行の見た目で
  mean / rms / blown / crushed を計測してテストに定数で記録する（これがないと「暗くなっていない」を証明できない）
- 実装後は「主光の強度」と「露出」の2値だけで ±20% に合わせる
- CON-05: レティクルを hudS へ移す変更は、F2-T05/T06（色・不透明度・黒背景上の画素値）を先に合格させてから照明を変える

### F3 スポナー・セクター
- `Spawner` は Three.js に依存しない純粋ロジックとして先に作り、公平性テスト（1000 シード × 8 パターン × 4 速度）を通してからゲームに組み込む
- 600 秒の早回しシミュレーションで、プール上限・セクター遷移・霧の視認時間を検証
- サイトの説明・開始メニューの「速度は時間とともに上昇」を同時に更新

### F4 岩マテリアル
- トライプラナーは `#define TRIPLANAR` で ON/OFF できる作りにし、OFF 時の見た目でも輝度テストが通ることを確認
- 影は PC の L0 のみ。draw call 予算の改訂（140→155）はこのフェーズでのみ行う

### F5 スコア・手応え
- ニアミスは F1 の `clearance` をそのまま使う（判定の二重実装をしない）
- SP の HUD は 1 行追加まで（過去FB: 左上の占有）

### F6 機体・空間・仕上げ
- 排気は `parts.exhaust[i].scale.y = 長さ` の互換を保つ（既存テスト・Sortie のコードを変えない）
- 仕上げの追加後に CON-05 テストを再実行

### F7 称号・デイリー・共有・文書
- 最後に、全文書（サイト本文・README・DESIGN・specs/00・JSON-LD）の整合を一括確認
- `labs/lookdev.html` を完了後の状態で再生成し、before / after を残す

## 4. テスト戦略

| 観点 | 方法 |
|---|---|
| 数値ロジック（判定・公平性・スコア・シード） | 純粋関数のユニットテスト（大量試行: 判定 500 方向 × 8、公平性 1000 × 8 × 4） |
| 見た目の劣化防止 | 固定配置の輝度プローブ（平均・コントラスト・白飛び・黒つぶれ）を基準 ±20% で監視 |
| CON-05 | マテリアル値の不変 + 黒背景上のレティクル画素値 + パス順序の 3 点で固定 |
| 性能 | draw call 予算、判定 / 生成の1回あたりの時間、Quality 縮退段の動作 |
| SP | 既存の SP テスト（横画面・HUD 占有・モーダル）+ 新規 HUD の高さ制約 |
| 回帰 | run-all（既存 12 スイート + F1〜F7）を各フェーズ末に全実行 |

## 6. リスク管理

| リスク | 対策 |
|---|---|
| 画面が暗くなる（過去FB の再発） | F2 で基準値を先に取り、F2・F4・F6 の各フェーズで輝度テストを必須化 |
| レティクルの見た目が変わる（CON-05） | hud パス方式 + 画素値テスト。仕上げやトーンマップはすべて hud パスより前 |
| 難度が上がりすぎる | 翼判定は寛容係数、生成は公平性検証、セクター1は現行より易しい速度上限（220） |
| SP の性能低下 | SP は Quality L1 開始（影・色収差・ノイズなし）、テクスチャ 256²、ダスト半減、合成パス追加なし（サイト） |
| 1 フェーズが大きくなりすぎる（F3） | F3 は内部を「F3a: Spawner + 公平性（純粋ロジック）」→「F3b: ゲーム組込 + セクター演出」の 2 コミットに分ける |
| 途中のフェーズで本番が中途半端な状態になる | 各フェーズ単体でゲームとして完結する順序にしてある（例: F2 完了時点で照明は全面移行済み、F3 完了時点で生成は全面移行済み） |
